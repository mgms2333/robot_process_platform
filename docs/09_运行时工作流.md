# 运行时工作流

## 目标

运行时层负责把已经生成好的 `Task` 按统一执行模型稳定推进，并向外提供可控的启动、暂停、恢复、停止和急停入口。

运行时层不负责：

- 模板解析
- 任务创建
- 机器人底层伺服控制
- 运动插补
- 相机或机器人 SDK 的底层连接细节
- 机器人选型和连接准备

运行时层负责：

- 接收要执行的 `Task`
- 控制任务生命周期
- 按 `ExecutionBlock -> Action` 推进任务
- 记录执行位置和错误状态
- 对外暴露状态快照

## 当前执行对象

运行时当前消费的统一对象为：

```text
Task
  -> ExecutionBlock
      -> Action
```

含义是：

- `Task` 表示一整个任务实例
- `ExecutionBlock` 表示一个可调度的连续执行块
- `Action` 表示执行器一次推进的最小动作单元

当前 `Tick()` 粒度是：

```
一次 Tick 最多执行一个 Action
```

## 当前底层组件

当前运行时已经具备以下底层组件：

- `RuntimeService`
- `TaskRunner`
- `StateMachine`
- `BlockScheduler`
- `BlockQueue`
- `BlockExecutor`
- `ExecutionContext`

它们的职责分别是：

- `TaskRunner`
  负责把整个运行时执行链串起来
- `StateMachine`
  负责状态迁移是否合法
- `BlockScheduler`
  负责选择下一个应该进入执行链的 `ExecutionBlock`
- `BlockQueue`
  负责保存当前 active block
- `BlockExecutor`
  负责执行当前 action
- `ExecutionContext`
  负责记录运行状态、当前位置和错误信息

## 当前已落地状态

当前项目里，`RuntimeService` 已经有最小代码骨架，具备：

- `StartService / StopService`
- 命令提交接口
- 线程主循环
- 命令串行处理
- `Running` 状态下调用 `TaskRunner::Tick()`
- `ExecutionContext` 快照读取

当前还没有接入：

- EventBus
- SafetyManager
- DeviceManager 事件
- task_id 自动读取任务文件
- 优先级命令队列

## 推荐运行方式

系统级运行时不应由外部循环直接反复调用 `TaskRunner::Tick()`。

推荐结构是：

```
HMI / API / Safety / Device
        |
        v
RuntimeService
        |
        v
TaskRunner
        |
        v
StateMachine / Scheduler / Queue / Executor
```

其中：

- `RuntimeService` 是线程宿主
- `TaskRunner` 是调度核心

## RuntimeService 工作流

`RuntimeService` 启动后应常驻运行，但不等于一启动就执行任务。

当前推荐工作流如下：

```
系统启动
  -> 初始化日志、模板管理、任务管理、设备
  -> 启动 RuntimeService 线程
  -> RuntimeService 进入空闲循环
  -> 等待外部命令
```

当前 `apps/runner/main.cpp` 使用的标准示例启动链为：

```text
初始化 Logger
  -> 创建 TemplateManager / TaskManager / Robot / RuntimeService
  -> 加载模板库
  -> 启动 RuntimeService
  -> 读取任务上下文 json
  -> CreateAndSaveTask
  -> LoadTask(task_id)
  -> SubmitLoadTask(task)
  -> SubmitStartTask()
  -> 主线程轮询 GetContextSnapshot()
  -> 等待 runtime_state 进入终态
  -> StopService()
  -> 输出执行结果
```

当前 `runner` 默认使用：

- 固定测试 json 路径
- `HyRobot` mock 模式

因此它当前更接近平台主链演示入口，而不是最终 HMI 入口。

外部命令主要包括：

- `LoadTask`
- `StartTask`
- `PauseTask`
- `ResumeTask`
- `StopTask`
- `EmergencyStop`
- `ResetFault`

运行时主执行流可表示为：

```text
json + template_name
        │
        ▼
TemplateManager
        │
        ▼
Template Plugin
        │
        ▼
TaskManager
        │
        ├── 保存 task.json
        │
        └── 读取 task.json -> Task
                           │
                           ▼
                    RuntimeService
                           │
                    Load / Start / Pause / Stop
                           │
                           ▼
                       TaskRunner
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
    StateMachine     BlockScheduler     ExecutionContext
                           │
                           ▼
                       BlockQueue
                           │
                           ▼
                      BlockExecutor
                           │
                           ▼
                    IRobot / ICamera
                           │
                           ▼
                     厂家 SDK / 控制器
```

## RuntimeService 单周期顺序

`RuntimeService` 线程每个周期不只做 `Tick()`，而是按固定顺序处理：

```
1. 处理外部命令
2. 判断当前是否收到停止服务请求
3. 判断当前是否允许推进任务
4. 如果允许，则调用 TaskRunner::Tick()
5. 等待下一周期或被新命令唤醒
```

展开后可以写成：

```text
while (service_running)
{
    ProcessPendingCommands();

    if (execution_context.runtime_state == Running)
    {
        task_runner.Tick(execution_context);
    }

    WaitNextCycleOrWakeup();
}
```

## Task 生命周期

`TaskRunner` 当前只保存正在执行任务的指针，不复制整个 `Task`。

因此 `RuntimeService` 需要自己持有当前运行中的 `Task` 实例，再把该实例传给 `TaskRunner::LoadTask()`。

这条约束的含义是：

- 命令队列里的临时 `Task` 载荷不能直接作为长期执行对象。
- `Task` 的真实存储应由 `RuntimeService` 在任务运行期间持有。
- 任务结束、停止或服务关闭后，`RuntimeService` 再释放该 `Task`。

## 命令来源

`TaskRunner` 不直接接收 HMI 或安全系统的跨线程调用。

当前实现原则是：

- 外部线程不直接修改 `ExecutionContext`
- 外部线程不直接调用 `Tick()`
- 外部线程只提交命令给 `RuntimeService`
- `RuntimeService` 在线程内串行调用 `TaskRunner`

这样可以避免多个来源同时改 runtime 状态。

## 机器人准备边界

运行时默认假定传入的 `IRobot` 已经处于可执行状态。

例如：

- 机器人型号已选定
- 机器人对象已创建
- 如有需要，SDK 已显式连接
- signal name 到 bit 的映射已由设备配置准备完成

这些内容属于平台或设备准备流程，不属于 `TaskRunner::Tick()` 的职责。

## 状态推进

当前推荐的状态推进关系如下：

```text
Idle
  -> TaskLoaded
Ready
  -> StartRequested
Running
  -> PauseRequested
Paused
  -> ResumeRequested
Running
  -> StopRequested
Stopped
Running
  -> TaskCompleted
Completed
Running
  -> BlockFailed
Failed
任意运行中状态
  -> EmergencyStopTriggered
EmergencyStop
```

## 暂停和急停语义

当前平台语义上：

- `Pause`
  阻止后续 action 继续推进
- `EmergencyStop`
  使 runtime 进入急停态并停止继续推进

需要注意：

- 这不等于底层机器人正在执行的运动一定能被中途切断
- 真正的运动中断能力要由 `IRobot` 或具体设备适配层提供

因此运行时控制分为两层：

- 平台层控制是否推进下一个 action
- 设备层控制当前动作能否被立即中断

## 错误记录

运行时错误当前通过 `ExecutionContext` 记录：

- `last_error_code`
- `last_error`

其中：

- `last_error_code` 用于程序判断
- `last_error` 用于日志和界面显示

这两者应始终一起维护，而不是只保留字符串。

## 恢复点

当前恢复起点由以下信息决定：

- `start_block_index`
- `start_action_index`

推荐后续正式恢复点对象至少包含：

- `task_id`
- `block_index`
- `action_index`
- `block_name`
- `semantic_type`
- `semantic_index`

这样恢复时不只按索引定位，还能校验恢复点是否仍然指向原来的语义块。

## 当前阶段结论

当前项目已经具备：

- `Task` 生成
- `Task` 持久化
- `Task` 重新加载
- `TaskRunner` 按 action 推进执行

下一阶段重点是继续把 `RuntimeService` 接入系统主入口，并在其上继续补命令优先级、事件、设备与安全输入。
