# 系统架构详解

## 1. 文档目标

本文档用于系统性介绍当前 `robot_process_platform` 的整体架构、模块职责、模块之间的交互关系，以及当前实现状态和后续演进方向。

文档面向的读者包括：

- 新加入项目的开发同事
- 负责 HMI、外部接口、设备接入的协作者
- 需要从整体上理解系统边界和数据流的人

本文档强调两点：

- 以**当前真实代码实现**为准
- 同时标出已经明确的设计方向，避免把“现状”和“目标”混淆

---

## 2. 系统定位

本项目是一套通用机器人工艺控制平台。

它位于：

```text
外部业务系统 / HMI / PLC / API
        ↓
系统协调与任务平台
        ↓
运行时执行链
        ↓
机器人 / 相机 / IO / 其他外设
```

它的核心职责不是直接做底层运动控制，而是：

- 管理工艺模板
- 根据输入 JSON 生成统一任务模型
- 保存与加载任务
- 按统一运行时模型执行任务
- 通过统一设备抽象驱动机器人和其他设备

换句话说，它是一个：

```text
把“工艺意图”转换成“统一任务执行”的系统中枢
```

---

## 3. 设计目标

系统目前围绕以下设计目标组织：

### 3.1 模板和执行解耦

模板不直接控制机器人。

模板的职责是：

- 解析业务 JSON
- 生成统一 `Task`

执行链的职责是：

- 消费 `Task`
- 推进执行
- 调用设备

### 3.2 设备品牌解耦

运行时不直接依赖某个厂家 SDK。

运行时只依赖：

- `IRobot`
- `ICamera`

设备品牌差异由设备适配层消化。

### 3.3 系统协调和运行时执行解耦

系统层负责：

- 初始化
- 设备选择
- 设备连接
- 任务创建
- 任务启动

运行时层负责：

- 装载任务
- 状态迁移
- 调度 block / action
- 执行动作

### 3.4 状态变化主动播报

运行时状态变化不应只靠外部轮询。

当前设计方向是：

```text
状态变化以主动播报为主
状态快照查询为补充
```

## 4. 整体分层

当前系统可以分为 6 个主要层次。

### 4.1 外部接口层

包括：

- HMI
- Runner
- 未来 REST API
- 未来 Modbus 接入
- 未来 PLC / MES / WCS 等控制入口

职责：

- 接收用户或外部系统命令
- 把外部协议转换成平台内部业务动作
- 展示状态和结果

### 4.2 系统协调层

当前核心对象：

- `SystemService`

职责：

- 对外提供统一业务入口
- 协调模板、任务、设备、运行时四条主链
- 管理系统初始化和待机逻辑
- 统一对外暴露系统状态与运行时事实

### 4.3 平台管理层

包括：

- `TemplateManager`
- `TaskManager`
- `DeviceManager`
- `Logger`
- `SystemConfig`

职责：

- 模板插件管理
- 任务创建和持久化
- 设备注册和 active 设备选择
- 日志基础设施
- 系统配置加载

### 4.4 运行时服务层

包括：

- `RuntimeService`

职责：

- 作为 runtime 的线程宿主
- 管理命令队列
- 串行处理运行时控制命令
- 周期性推进 `TaskRunner::Tick()`
- 产出 runtime 状态事实

### 4.5 运行时执行层

包括：

- `TaskRunner`
- `StateMachine`
- `BlockScheduler`
- `BlockQueue`
- `BlockExecutor`
- `ExecutionContext`

职责：

- 推进任务执行
- 管理任务状态
- 记录执行位置
- 执行 `Action`

### 4.6 设备抽象与设备实现层

包括：

- `IRobot`
- `ICamera`
- `HyRobot`
- 未来其他 robot / camera adapter

职责：

- 向 runtime 提供统一动作接口
- 屏蔽不同设备、不同厂家 SDK 差异

## 6. 核心统一数据模型

当前系统的执行端统一消费以下模型：

```text
Task
  └── ExecutionBlock
      └── Action
```

### 6.1 Task

表示一次完整任务实例。

它至少包含：

- `task_id`
- `template_name`
- `execution_blocks`

### 6.2 ExecutionBlock

表示一个可以调度的连续执行块。

它的作用是：

- 作为运行时调度单元
- 承载一个有语义边界的动作组

例如在码垛场景里，一个 `ExecutionBlock` 可能表示：

- PickBlock
- ScanBlock
- TransferBlock
- PlaceBlock

### 6.3 Action

表示运行时执行器一次推进的最小动作单元。

当前 `Action` 包含：

- `action_name`
- `action_type`
- `action_parameters`
- `timeout_ms`

当前动作类型包括：

- `MoveJoint`
- `MoveLinear`
- `SetDigitalOutput`
- `WaitDigitalInput`
- `Delay`

当前参数模型仍是：

```cpp
std::map<std::string, std::string>
```

这意味着：

- 动作种类已经统一
- 参数格式仍以约定为主
- 后续可以进一步收紧为强类型参数结构

---

## 7. 模板链

模板链负责把外部输入转换成统一任务模型。

### 7.1 TemplateManager

职责：

- 加载模板 `.so`
- 卸载模板
- 创建模板实例
- 查询当前已加载模板列表

它回答的是：

```text
系统当前有哪些模板可用
如何根据模板名创建模板实例
```

### 7.2 TaskManager

职责：

- 调用模板生成 `Task`
- 保存 `Task` 到本地 JSON
- 从本地 JSON 读回 `Task`
- 删除任务

它回答的是：

```text
如何创建任务
如何持久化任务
如何重新加载任务
```

### 7.3 模板插件

当前模板插件示例是：

- `palletizing`

模板插件负责：

- 解析输入 JSON
- 生成模板语义层对象
- 展开为统一 `Task`

典型流程是：

```text
task_context_json
-> ParseTaskParameters
-> BuildProcessPlan
-> BuildTask
-> Task / ExecutionBlock / Action
```

### 7.4 模板链交互关系

```text
SystemService.CreateTask(...)
  -> TaskManager.CreateAndSaveTask(...)
      -> TemplateManager.CreateTemplate(template_name)
          -> Template Plugin
              -> ParseTaskParameters
              -> BuildProcessPlan
              -> BuildTask
      -> 保存 task json
```

## 8. 任务链

任务链的重点是：**创建和运行严格分离**。

这是当前系统已经明确收下来的原则。

### 8.1 创建任务

`CreateTask(...)` 的职责是：

- 根据模板和 JSON 生成 `Task`
- 保存到本地任务目录

它**不负责启动执行**。

### 8.2 运行任务

`StartTask(...)` 的职责是：

- 运行一个**已经存在的任务**
- 从指定 `block_index / action_index` 开始

当前语义已经收敛成：

```text
StartTask(task_id, task_dir, start_block_index, start_action_index)
```

因此：

- 默认从头运行：
  `StartTask(task_id, task_dir, 0, 0)`
- 断点恢复：
  `StartTask(task_id, task_dir, block_index, action_index)`

这条语义很重要，因为它保证：

```text
点击运行不等于每次重新创建一个新 task
```

---

## 9. SystemService：系统协调层核心

`SystemService` 是当前系统对外最重要的统一入口。

### 9.1 它的本质

一句话概括：

```text
SystemService 是系统统一业务协调入口
```

它的作用不是替代其他模块，而是把这些模块组织起来。

### 9.2 它协调哪些模块

当前主要协调：

- `TemplateManager`
- `TaskManager`
- `DeviceManager`
- `RuntimeService`

### 9.3 它负责什么

- 系统初始化
- 候选 robot 配置加载
- 默认选择项维护
- 手动连接选中 robot
- 创建任务
- 启动任务
- 暂停 / 恢复 / 停止任务
- 获取系统状态
- 获取 runtime 快照
- 接收 runtime facts 并对外转发

### 9.4 它不负责什么

- 不直接推进 `Tick()`
- 不直接实现状态机规则
- 不直接解析模板业务含义
- 不直接实现底层 SDK 调用
- 不负责机器人内部动作实现

### 9.5 为什么需要它

因为如果没有 `SystemService`，外部入口层就必须自己拼：

- 模板调用
- 任务调用
- 设备选择
- runtime 控制

这样很快会变成：

```text
HMI 拼一套
Runner 拼一套
Modbus 再拼一套
```

`SystemService` 的作用就是把这些流程收口。

---

## 10. SystemConfig：系统配置模块

为了让 `SystemService` 不再兼任配置解析器，现在已经引入了轻量配置模块：

- `system_config.h`
- `system_config.cpp`

### 10.1 作用

负责：

- 读取 `config/system_config.json`
- 解析候选 robot 列表
- 解析默认项
- 解析 `HyRobotConfig`

### 10.2 为什么单独拆出来

因为 `SystemService` 的职责应偏向：

```text
系统协调
```

而不是同时承担：

- JSON 文件读取
- JSON 字段解析
- `HyRobotConfig` 填充

当前这一步的目标不是做很重的配置系统，而只是把：

```text
配置结构 + 读取逻辑
```

从 `SystemService.cpp` 中挪出去。

### 10.3 当前配置文件的意义

当前 `config/system_config.json` 用来描述：

- 当前系统有哪些候选 robot
- 默认推荐项是哪一个
- 每个 robot 的配置参数是什么

当前已经支持：

- `type = "hy_robot"`

同时支持：

- `default: true`

其语义是：

```text
默认推荐项 / 默认选中项
```

而不是：

```text
系统一启动就必须马上创建并连接这个 robot
```

---

## 11. DeviceManager：设备管理层

`DeviceManager` 当前是一个轻量设备注册中心。

### 11.1 它负责什么

- 注册 robot
- 注销 robot
- 查询 robot
- 设置 active robot
- 查询 active robot

- 注册 camera
- 注销 camera
- 查询 camera
- 设置 active camera
- 查询 active camera

### 11.2 它不负责什么

- 不负责 runtime
- 不负责任务执行
- 不负责模板
- 不负责隐式设备连接

### 11.3 当前设计重点

`DeviceManager` 当前主要解决的是：

```text
系统里有哪些设备
当前使用哪一个设备
```

而不是：

```text
设备什么时候连接
任务怎么执行
```

### 11.4 和 SystemService 的关系

- `DeviceManager` 负责注册和 active 选择
- `SystemService` 负责业务流程，例如：
  - 选中某个配置项
  - 手动触发连接
  - 连接成功后注册到 `DeviceManager`
  - 设置 active robot
  - rebuild runtime

---

## 12. 设备选择与连接模型

这一部分是最近系统里非常关键的一步。

### 12.1 当前收下来的目标模型

系统启动后：

- 不立即创建具体 `HyRobot`
- 不立即自动连接
- 只加载候选配置和默认选择项

然后：

- 用户或入口层先选中一个 robot
- 再点击连接
- 这时才真正创建 `HyRobot` 对象并 `Connect()`

### 12.2 当前最小实现

目前这条线已经落成代码，语义如下：

#### `Initialize()`

当前做的是：

- 读取 `system_config.json`
- 加载候选 robot 信息
- 设置默认 `selected_robot_name`
- **不创建设备对象**
- **不创建 `RuntimeService`**

#### `ConnectSelectedRobot()`

当前做的是：

- 根据 `selected_robot_name` 找配置
- 当前只支持 `hy_robot`
- 创建 `HyRobot`
- 调 `HyRobot::Connect()`
- 注册到 `DeviceManager`
- 设为 active robot
- `RebuildRuntimeService()`

### 12.3 为什么这样更合理

因为它符合更真实的 HMI / 设备准备流程：

```text
选 robot
!=
创建设备对象
!=
连接设备
```

而不是在系统启动时偷偷完成这一切。

---

## 13. RuntimeService：运行时服务层

`RuntimeService` 是 runtime 子系统的统一服务入口。

### 13.1 它的本质

一句话概括：

```text
RuntimeService 是 runtime 的线程宿主和命令入口
```

### 13.2 它负责什么

- 启动运行时线程
- 停止运行时线程
- 接收运行时命令
- 串行处理命令
- 在 `Running` 状态下周期性调用 `TaskRunner::Tick()`
- 提供 `ExecutionContext` 快照
- 产生 `RuntimeFact`

### 13.3 它不负责什么

- 不解析模板
- 不创建任务
- 不选择 robot
- 不负责设备连接策略

### 13.4 为什么需要它

因为如果没有它，外部就容易写成：

```cpp
while (running)
{
    task_runner.Tick(...);
}
```

这样：

- 谁都能直接推进 runtime
- 命令难以串行化
- 线程边界混乱

`RuntimeService` 的存在就是为了把 runtime 的推进权收住。

---

## 14. TaskRunner：运行时执行编排器

`TaskRunner` 是真正的任务推进核心。

### 14.1 它负责什么

- 装载任务
- 启动任务
- 暂停 / 恢复 / 停止 / 急停 / 故障复位
- 推进 `Tick()`
- 记录执行位置
- 驱动状态机
- 组织 block 调度和 action 执行

### 14.2 它如何使用状态机

`TaskRunner` 内部直接组合了一个 `StateMachine` 成员。

当前不是注入引用，而是：

```text
TaskRunner 自己持有 StateMachine
```

并通过：

- `HandleStateTransition(...)`
- `CanPushBlockToQueue(...)`

来调用状态机规则。

### 14.3 当前状态值存在哪里

当前状态值不保存在 `StateMachine` 自己身上，而保存在：

- `ExecutionContext.runtime_state`

所以分工是：

- `ExecutionContext`
  保存当前状态值
- `StateMachine`
  负责“允许怎么变”
- `TaskRunner`
  负责“什么时候触发事件”

---

## 15. StateMachine：状态迁移规则器

`StateMachine` 当前的意义不是“保存状态”，而是：

```text
集中定义状态迁移规则
```

### 15.1 它解决什么问题

避免这些判断散落在 `TaskRunner` 的各个函数里：

- `Start()`
- `Pause()`
- `Resume()`
- `Stop()`
- `Tick()`

### 15.2 当前设计原则

```text
未定义的状态迁移 = 不允许
```

这使得运行时状态机具有比较强的边界。

---

## 16. BlockScheduler / BlockQueue / BlockExecutor

这三个模块共同构成运行时执行链的中间层。

### 16.1 BlockScheduler

职责：

- 在任务里选出下一个应该进入执行链的 `ExecutionBlock`

### 16.2 BlockQueue

职责：

- 保存当前 active block
- 管理 block 的进入和清理

### 16.3 BlockExecutor

职责：

- 看当前 `Action` 的 `action_type`
- 分发到统一设备接口

典型分发关系是：

```text
MoveJoint
  -> robot.MoveJoint(...)

MoveLinear
  -> robot.MoveLinear(...)

SetDigitalOutput
  -> robot.SetDigitalOutput(...)

WaitDigitalInput
  -> robot.WaitDigitalInput(...)
```

它不关心底下是 mock 还是真机 SDK。

---

## 17. ExecutionContext：运行时事实快照

`ExecutionContext` 用于保存运行时当前状态。

当前至少包括：

- `runtime_state`
- `current_block_index`
- `current_action_index`
- `last_error_code`
- `last_error`

它是：

```text
当前 runtime 事实的存储点
```

快照查询就是从这里拿。

---

## 18. RuntimeFact：运行时状态主动播报

这是系统最近新增的一条很重要的链路。

### 18.1 为什么要有它

因为状态变化不应该主要靠外部不停轮询。

更合理的设计是：

```text
runtime 自己知道状态变了
-> 主动播报事实
-> SystemService 统一向外转发
```

### 18.2 当前代码落点

在 `RuntimeService` 里有：

- `RuntimeFactType`
- `RuntimeFact`
- `RuntimeFactCallback`
- `SetRuntimeFactCallback(...)`

在 `RuntimeService.cpp` 里有：

- `BuildRuntimeFacts(...)`
- `EmitRuntimeFacts(...)`

### 18.3 当前最小事实类型

包括：

- `StateChanged`
- `TaskLoaded`
- `TaskStarted`
- `TaskPaused`
- `TaskResumed`
- `TaskStopped`
- `TaskCompleted`
- `TaskFailed`
- `TaskEmergencyStopped`
- `FaultReset`

### 18.4 当前传播链

```text
TaskRunner / RuntimeService
  -> RuntimeFact
  -> SystemService::HandleRuntimeFact(...)
  -> 对外回调出口
```

这还不是完整 EventBus，但已经是一个可用的最小主动播报链。

---

## 19. IRobot / ICamera：统一设备抽象

设备抽象层的目标是：

```text
让 runtime 只关心统一动作
不关心具体厂家 SDK
```

### 19.1 IRobot

当前统一机器人能力包括：

- `MoveJoint(...)`
- `MoveLinear(...)`
- `SetDigitalOutput(...)`
- `WaitDigitalInput(...)`
- `Delay(...)`

### 19.2 ICamera

当前先保留最小视觉能力抽象。

重点不是视觉算法，而是让系统知道：

```text
相机也是一个可被 runtime 或平台统一消费的设备
```

---

## 20. HyRobot：当前机器人实现

`HyRobot` 是当前默认的机器人实现。

### 20.1 当前双模式

- mock 模式
- 可选 Huayan SDK 模式

### 20.2 mock 模式的作用

用于：

- 验证系统主链
- 验证动作分发
- 验证日志
- 验证运行时推进

当前 `Connect()` 在 mock 模式下也会返回“模拟连接成功”，这样整条：

```text
Initialize -> ConnectSelectedRobot -> StartTask
```

就能完整跑通。

### 20.3 真机模式的意义

当开启华沿 SDK 构建选项后，`HyRobot` 会落到底层 SDK 能力。

这让同一条系统主链可以在：

- mock
- 真机

之间切换，而不需要改 runtime 逻辑。

---

## 21. 启动到待机的当前真实流程

当前 runner 下，系统从启动到待机再到执行的大致流程是：

### 21.1 初始化阶段

```text
main
  -> Logger.Initialize()
  -> 创建 SystemService
  -> SystemService.Initialize(system_config.json, false)
      -> LoadSystemConfig(...)
      -> 加载候选 robot 配置
      -> 设置 selected_robot_name
      -> 不创建设备对象
```

这时系统已经初始化，但还没有 active robot，也没有 runtime service。

### 21.2 连接设备阶段

```text
main
  -> SystemService.ConnectSelectedRobot()
      -> 创建 HyRobot
      -> HyRobot.Connect()
      -> DeviceManager.RegisterRobot(...)
      -> DeviceManager.SetActiveRobot(...)
      -> RebuildRuntimeService()
          -> 创建 RuntimeService(active_robot)
          -> StartService()
```

这时系统进入：

```text
设备已就绪，可执行任务
```

这就是当前更贴近 HMI 的“先选、后连”流程。

## 22. 当前任务创建与执行流程

### 22.1 创建任务

```text
main / HMI / API
  -> SystemService.CreateTask(template_name, task_context_json, task_dir)
      -> TaskManager.CreateAndSaveTask(...)
      -> TemplateManager.CreateTemplate(...)
      -> Template Plugin 生成 Task
      -> 保存 task json
```

### 22.2 启动任务

```text
main / HMI / API
  -> SystemService.StartTask(task_id, task_dir, 0, 0)
      -> TaskManager.LoadTask(task_id)
      -> RuntimeService.SubmitLoadTask(task, 0, 0)
      -> RuntimeService.SubmitStartTask()
```

### 22.3 runtime 内部执行

```text
RuntimeService 线程
  -> ProcessPendingCommands()
  -> LoadTask
  -> StartTask
  -> TickIfRunning()
      -> TaskRunner.Tick()
          -> BlockScheduler
          -> BlockQueue
          -> BlockExecutor
              -> IRobot
                  -> HyRobot
```

### 22.4 状态传播

```text
TaskRunner / RuntimeService
  -> RuntimeFact
  -> SystemService
  -> 外部接口层
```

## 23. 当前架构的主要优点

### 23.1 边界比较清楚

- 模板不控制设备
- runtime 不负责设备选型和连接
- SystemService 不直接推进 action

### 23.2 主链已经能跑

当前不是“只有设计”，而是：

- 能创建任务
- 能保存 / 读取任务
- 能启动 runtime
- 能执行到 `Completed`

### 23.3 设备接入路径已经清楚

通过 `IRobot` 抽象，后续接更多 robot 时不必重写 runtime 主链。

### 23.4 状态传播方向已经立住

虽然还没完整 EventBus，但已经从“只有轮询”走向“有最小主动播报出口”。

---

## 24. 当前仍需继续演进的部分

### 24.1 SystemService 仍然知道 `HyRobot`

当前它仍有一些华沿专用逻辑，例如：

- 只支持 `hy_robot`
- 仍有 `GetActiveHyRobot()`
- 连接逻辑仍特判 `HyRobot`

这在当前阶段可接受，但后续应继续向“工厂化设备创建”收敛。

### 24.2 动作参数仍偏松

当前 `Action` 参数仍然是：

```cpp
std::map<std::string, std::string>
```

后续如果真机类型增多，建议逐步把关键动作的参数语义收紧。

### 24.3 外部接口层还未实体化

当前 HMI / Modbus / API 只是架构位置已经定好，还没有真正做成独立的接口模块。

### 24.4 完整事件系统还没落地

当前只有最小 `RuntimeFact` 链，还不是完整 EventBus。

## 25. 向外介绍这套系统时的推荐说法

如果你要对别人介绍这套系统，可以用下面这段作为核心表述：

```text
这套系统的核心思路是：
上层通过模板和 JSON 生成统一 Task，
SystemService 负责统一协调模板、任务、设备和运行时，
RuntimeService 在线程里驱动 TaskRunner 按 Action 推进任务，
运行时通过 IRobot / ICamera 统一接口调用设备，
最终由具体设备适配层落到底层 SDK 或 mock 执行。

系统启动时先加载候选设备配置，不立即创建设备对象；
只有在显式连接某个选中 robot 时，才真正创建对应设备对象并连接，
再由系统重建 RuntimeService 绑定该 robot。

运行过程中，状态变化由 runtime 主动产出 RuntimeFact，
再由 SystemService 统一向外暴露，而不是主要靠外部轮询推导状态。
```

## 26. 一句话总结

当前系统已经形成了这样一套清晰主线：

```text
外部接口层发起业务动作
-> SystemService 统一协调
-> Template / Task / Device / Runtime 各司其职
-> RuntimeService 驱动 TaskRunner 执行 Task
-> 统一设备抽象承接动作
-> 具体设备实现落到底层 SDK
-> 状态变化通过 RuntimeFact 主动向外播报
```

这意味着它已经不再只是一个运行时 demo，而是一套开始具备系统级架构边界、设备接入边界和外部控制边界的机器人控制平台底座。
