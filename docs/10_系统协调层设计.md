# 系统协调层设计

## 定位

系统协调层用于把平台内部已经存在的多个子系统组织成统一的业务入口。

当前子系统包括：

- `TemplateManager`
- `TaskManager`
- `DeviceManager`
- `RuntimeService`

系统协调层的目标不是替代这些子系统，而是对外暴露稳定、清晰、统一的系统级接口。

推荐命名：

- `SystemService`
- 或 `SystemController`

当前文档统一使用 `SystemService`。

## 核心职责

`SystemService` 负责：

- 初始化平台基础对象。
- 协调模板、任务、设备、运行时四条主链。
- 对 HMI / API / Runner / 未来 Modbus 接口暴露统一业务接口。
- 组织“选设备 -> 连接设备 -> 创建任务 -> 启动执行”的完整作业流程。
- 提供系统级状态查询入口。
- 对外提供统一的平台状态变化播报出口。

`SystemService` 不负责：

- 实现模板生成逻辑。
- 实现任务持久化细节。
- 实现 runtime 调度推进。
- 实现机器人或相机 SDK 细节。
- 在内部持有独立执行线程替代 `RuntimeService`。

## 在整体架构中的位置

```text
HMI / Runner / API / Modbus
          |
          v
  外部接口层适配
          |
          v
   SystemService
   |        |        |        |
   v        v        v        v
Template   Task     Device   Runtime
Manager    Manager  Manager  Service
```

也就是说：

- HMI 不直接调用 `TaskRunner`
- HMI 不直接调用 `TemplateManager`
- HMI 不直接操作 `DeviceManager` 内部结构
- HMI 优先通过 `SystemService` 完成系统级业务动作
- 未来 Modbus 也不直接驱动 runtime，而是先转换成平台内部业务动作，再交给 `SystemService`

## 外部接口层补充说明

平台后续不应假设只有 HMI 会控制系统。

更合理的入口模型是：

- HMI
- Runner
- REST API
- Modbus
- 未来其他 PLC / 上位机协议

这些入口都属于外部接口层。

它们的职责是：

- 接收用户或外部系统命令
- 解析各自协议
- 转换成平台内部统一业务动作
- 调用 `SystemService`

因此：

- HMI 不是平台业务逻辑层
- Modbus 也不是 runtime 层
- 它们最终都应汇聚到 `SystemService`

## 持有关系

推荐的持有关系如下：

```text
SystemService
  ├── TemplateManager
  ├── TaskManager
  ├── DeviceManager
  ├── RuntimeService（按需创建或重建）
  └── 未来可扩展：
      ├── EventBus
      ├── SafetyManager
      └── AlarmManager
```

其中有一个关键点：

`TaskManager` 依赖 `TemplateManager`，因此 `SystemService` 内部构造顺序需要保证：

```text
TemplateManager
-> TaskManager
```

`RuntimeService` 依赖一个已经选定的 `IRobot`，因此它的创建顺序需要保证：

```text
DeviceManager 已有 active robot
-> RuntimeService 才能创建
```

## 模块关系总览

为了避免只看到单个 manager 或单个 service 时失去全局视角，下面把当前系统的主要模块关系统一写成树状结构。

### 1. 整体模块关系

```text
外部接口层
  ├── HMI
  ├── Runner
  ├── REST API（未来）
  ├── Modbus（未来）
  └── 其他 PLC / 上位机协议（未来）
      └── 统一调用 SystemService

SystemService
  ├── TemplateManager
  ├── TaskManager
  ├── DeviceManager
  ├── RuntimeService（按需创建或重建）
  └── 未来可扩展
      ├── EventBus
      ├── SafetyManager
      └── AlarmManager

DeviceManager
  ├── active robot
  ├── active camera
  ├── registered robots
  └── registered cameras

RuntimeService
  └── TaskRunner
      ├── StateMachine
      ├── BlockScheduler
      ├── BlockQueue
      ├── BlockExecutor
      └── ExecutionContext

设备抽象层
  ├── IRobot
  └── ICamera

设备实现层
  ├── HyRobot
  ├── 未来 Camera Adapter
  └── 未来其他厂家 Robot Adapter
```

### 2. 任务生成关系

```text
外部接口层
  └── SystemService.CreateTask(...)

SystemService
  └── TaskManager
      └── TemplateManager
          └── Template Plugin
              ├── ParseTaskParameters
              ├── BuildProcessPlan
              └── BuildTask
                  └── 输出 Task
                      └── ExecutionBlock
                          └── Action
```

这里的关键关系是：

- `SystemService` 只组织创建流程
- `TaskManager` 负责生成、保存、读取任务
- `TemplateManager` 负责创建模板实例
- 模板插件负责把输入 JSON 转成统一 `Task`

### 3. 任务执行关系

```text
外部接口层
  └── SystemService.StartTask(task_id, task_dir, start_block_index, start_action_index)

SystemService
  ├── TaskManager.LoadTask(...)
  └── RuntimeService
      ├── SubmitLoadTask(task, start_block_index, start_action_index)
      ├── SubmitStartTask()
      └── 线程循环
          └── TaskRunner.Tick()
              ├── StateMachine
              ├── BlockScheduler
              ├── BlockQueue
              ├── BlockExecutor
              │   └── IRobot
              │       └── HyRobot / 其他 robot adapter
              └── ExecutionContext
```

这里的关键关系是：

- `SystemService` 负责把已有任务交给 runtime
- `RuntimeService` 负责线程和命令串行化
- `TaskRunner` 负责推进执行
- `BlockExecutor` 负责把 `Action` 分发到统一设备接口

### 4. 状态传播关系

```text
TaskRunner / RuntimeService
  └── 识别运行时状态变化
      └── RuntimeFact
          └── SystemService
              └── 外部接口层
                  ├── HMI
                  ├── Modbus（未来）
                  ├── REST API（未来）
                  └── 其他外部订阅者（未来）
```

这里的关键关系是：

- runtime 状态变化首先发生在 runtime 内部
- `RuntimeService` 产生最接近事实的运行时事件
- `SystemService` 负责把这些事实变成统一系统出口
- 外部接口层消费平台播报结果，而不是各自盯 runtime 细节

## 对外业务接口设计

当前阶段推荐把 `SystemService` 对外接口分成两大类：

- 公共接口
- 分对象接口

同时还需要提前确认一个原则：

```text
SystemService 不应只提供“给外部读取状态”的接口，
还应成为平台统一状态播报的出口。
```

这意味着后续无论状态来自：

- runtime
- device
- safety
- alarm

都应由平台统一向外部接口层播报，而不是让各入口各自轮询各自解释。

### 1. 公共接口

这部分不直接偏向模板、任务或 runtime，而是平台整体入口。

建议包括：

- `Initialize()`
- `Shutdown()`
- `GetSystemState()`

职责：

- 初始化平台对象。
- 加载系统配置与候选设备信息。
- 在显式连接后启动运行时服务。
- 清理运行时和资源。
- 对外提供平台级状态。
- 对外提供平台级状态变化广播出口。

### 2. 模板相关接口

这部分统一归模板链和模板管理职责。

建议包括：

- `LoadTemplateLibrary(shared_library_path)`
- `UnloadTemplate(template_name)`
- `GetLoadedTemplates()`

职责：

- 面向 HMI 展示可用模板。
- 管理模板插件生命周期。
- 为任务创建提供模板来源。

### 3. 设备相关接口

这部分统一归设备链和 `DeviceManager` 职责。

当前实现中已有：

- `RegisterRobot(robot_name, robot_ptr)`
- `RegisterCamera(camera_name, camera_ptr)`
- `SetActiveRobot(robot_name)`
- `SetActiveCamera(camera_name)`
- `GetActiveRobot()`
- `GetActiveCamera()`
- `ConnectActiveRobot()`
- `DisconnectActiveRobot()`

这些接口更偏向：

```text
设备对象已经存在后的注册、选择和连接
```

职责：

- 管理当前平台可用设备。
- 管理 active robot / camera。
- 组织设备准备流程。

注意：

- `DeviceManager` 负责注册和 active 选择。
- `SystemService` 负责把“active 选择”和“连接动作”组织成业务流程。

### 设备相关接口的目标收敛方向

如果后续采用“先在 HMI 选中 robot，再点击连接时才创建设备对象”的模式，那么 `SystemService` 的设备接口语义应进一步收敛。

更推荐的目标接口面是：

- `GetConfiguredRobots()`
- `GetDefaultRobotName()`
- `GetSelectedRobotName()`
- `SelectConfiguredRobot(robot_name)`
- `ConnectSelectedRobot()`
- `DisconnectActiveRobot()`
- `GetActiveRobot()`

其中：

- `GetConfiguredRobots()`
  返回配置文件中可供创建的 robot 条目列表
- `GetDefaultRobotName()`
  返回配置文件中 `default = true` 的默认推荐项
- `GetSelectedRobotName()`
  返回当前在系统内被选中的 robot 配置项名称
- `SelectConfiguredRobot(robot_name)`
  只记录“当前用户想连哪台 robot”，不立刻创建设备对象
- `ConnectSelectedRobot()`
  这时才根据已选条目：
  - 创建设备对象
  - 调用 `Connect()`
  - 注册到 `DeviceManager`
  - 设为 active robot
  - `RebuildRuntimeService()`

也就是说，目标模型下：

```text
Select
!=
Create
!=
Connect
```

这三个动作应严格分开。

### 当前实现与目标实现的区别

当前实现更接近：

```text
Initialize()
  -> 读取候选 robot 配置与默认标记
  -> 设置 selected robot
  -> 不创建设备对象

ConnectSelectedRobot()
  -> 创建设备对象
  -> Connect()
  -> RegisterRobot(...)
  -> SetActiveRobot(...)
  -> RebuildRuntimeService()
```

目标实现更接近：

```text
Initialize()
  -> 只读取 robot 候选配置和默认标记
  -> 不创建设备对象

HMI SelectConfiguredRobot(robot_name)
  -> 只更新当前选择

HMI ConnectSelectedRobot()
  -> 创建设备对象
  -> Connect()
  -> RegisterRobot(...)
  -> SetActiveRobot(...)
  -> RebuildRuntimeService()
```

当前阶段建议先把接口语义和配置结构收稳，再逐步把现有实现切到目标模式。

### 4. 任务相关接口

这部分统一归模板生成任务和任务文件管理职责。

建议包括：

- `CreateTask(template_name, task_context_json)`
- `LoadTask(task_id)`
- `DeleteTask(task_id)`

职责：

- 面向 HMI 或 API 暴露统一任务入口。
- 调用 `TaskManager` 完成任务创建、读取和删除。

### 5. 执行相关接口

这部分统一归 runtime 和 task 执行职责。

建议包括：

- `StartTask(task_id, task_dir, start_block_index, start_action_index)`
- `PauseTask()`
- `ResumeTask()`
- `StopTask()`
- `EmergencyStopTask()`
- `ResetFault()`
- `GetRuntimeSnapshot()`

职责：

- 把已保存任务装载到 runtime，并从指定 block/action 位置启动。
- 对外暴露 runtime 状态快照。
- 对外暴露 runtime 状态变化事实。

## 平台状态传播原则

平台后续应采用：

```text
状态变化主动播报为主
状态快照查询为辅
```

对外接口层的典型行为应是：

- 启动时拉取一次当前平台状态或 runtime 快照
- 运行过程中主要靠平台主动播报状态变化

而不应是：

- HMI 持续高频轮询
- Modbus 控制端自己维护一套状态推导逻辑
- 每个外部入口都各自判断平台当前状态

因此后续 `SystemService` 至少应统一承接：

- runtime 状态变化
- 设备连接状态变化
- 未来安全/报警状态变化

再由外部接口层按各自协议消费，例如：

- HMI 直接刷新页面
- Modbus 把状态映射为线圈 / 寄存器
- REST API 通过 SSE / WebSocket 推送

## 启动流程设计

完整系统启动后，`SystemService` 应组织如下流程：

```text
程序启动
  -> 初始化 Logger
  -> 创建 TemplateManager
  -> 创建 TaskManager
  -> 创建 DeviceManager
  -> 从 `config/system_config.json` 读取候选设备与默认标记
  -> 设置默认 selected robot
  -> 不立即创建设备对象
  -> 进入待机状态
```

需要注意：

- `RuntimeService` 不再要求在 `Initialize()` 阶段立即创建。
- 启动完成后系统应处于“平台在线，等待外部业务命令”的状态。

### 默认设备策略

当前配置文件示例为：

```text
config/system_config.json
```

配置中至少描述：

- `devices.robots[].name`
- `devices.robots[].type`
- `devices.robots[].default`
- `devices.robots[].config`

其中：

- `default = true`
  表示该设备条目是系统默认推荐项
- 这个默认标记更适合用于：
  - HMI 初次打开时默认选中哪种 robot
  - Runner / 调试入口未显式指定设备时的默认选择

当前已支持 `type = "hy_robot"`，并把 `HyRobotConfig` 中的连接、运动默认值和 IO 映射从 JSON 读入。

推荐约束：

- `default = true` 在同类设备中应至多出现一次
- 默认标记只用于“默认选中”
- 默认标记不应直接等价于“系统启动时自动建连”

如果默认配置文件不存在，平台只回退到内置 mock hy robot 默认值，避免调试环境直接失败；现场地址不再写死在代码中。

需要注意：

- 默认标记不等于默认已经创建 active robot
- 是否在 `Initialize()` 阶段自动连接，属于平台策略问题

当前建议分两种模式：

- 调试模式：`Initialize()` 后由入口代码显式调用 `ConnectSelectedRobot()`
- 正式 HMI 模式：由用户在界面点击“连接机器人”后再执行 `ConnectSelectedRobot()`

### HMI 显式选择与连接目标流程

后续更推荐的交互模型不是“系统启动时就创建具体 robot 对象”，而是：

```text
系统启动
  -> SystemService 初始化基础对象
  -> HMI 展示可选 robot 类型和默认标记
  -> 用户选中某个 robot 条目
  -> 用户点击“连接”
  -> SystemService 根据 type + config 创建设备对象
  -> 调用该设备对象的 Connect()
  -> 连接成功后注册到 DeviceManager
  -> 设为 active robot
  -> RebuildRuntimeService()
  -> 系统进入“设备已就绪，可执行任务”状态
```

这条流程意味着：

- “选择 robot” 和 “连接 robot” 是两步
- 默认 tag 只表示默认推荐项，不等于启动时必须立刻创建设备对象
- 真正的设备对象创建和 `Connect()` 调用，应该发生在用户点击“连接”之后

当前代码已经切到这套模式的最小实现。当前实际行为更接近：

```text
Initialize()
  -> 读取候选设备配置和默认标记
  -> 只设置 selected robot

ConnectSelectedRobot()
  -> 创建 hy_robot
  -> Connect()
  -> RegisterRobot(...)
  -> SetActiveRobot(...)
  -> RebuildRuntimeService()
```

因此这里要区分：

- **当前实现**
  已支持“初始化不创建设备对象，点击连接时再创建并连接”
- **后续目标**
  继续把设备类型构造逻辑从 `SystemService` 中拆薄

## 作业流程设计

### 方式一：创建任务

```text
HMI 提交 template_name + task_context_json
  -> TaskManager 创建并保存 Task
  -> 返回 task_id
```

适用场景：

- 现场直接下发新任务
- 调试或单次执行前先生成任务文件

### 方式二：从 task_id 启动

```text
HMI 提交 task_id + start_block_index + start_action_index
  -> SystemService 检查 active robot 是否存在
  -> TaskManager.LoadTask(task_id)
  -> RuntimeService.SubmitLoadTask(task, start_block_index, start_action_index)
  -> RuntimeService.SubmitStartTask()
```

适用场景：

- 历史任务重跑
- 任务列表启动
- 断点恢复或指定步骤重跑

## 设备准备流程设计

当前设计里，设备准备流程应明确独立于 runtime 执行流程。

推荐流程：

```text
HMI 选择 robot
  -> SystemService.SelectConfiguredRobot(robot_name)
  -> SystemService.ConnectSelectedRobot()
  -> 设备准备完成
  -> 之后才允许 StartTask
```

也就是说：

- 设备连接不是 `TaskRunner` 的职责
- 设备连接不是某个 `Action`
- 设备连接是作业前置准备动作

## Runtime 依赖关系设计

`RuntimeService` 不应该在运行过程中动态查找设备。

推荐原则：

- `RuntimeService` 消费一个已经选定、已经准备好的 `IRobot`
- 平台切换 robot 时，应由 `SystemService` 协调停 runtime、切设备、重建 runtime

推荐切换流程：

```text
Stop RuntimeService
  -> SelectConfiguredRobot(new_robot)
  -> ConnectSelectedRobot()
  -> Rebuild RuntimeService(active_robot)
```

## 为什么需要这一层

如果没有 `SystemService`，系统容易出现这些问题：

- HMI 直接操作多个 manager，调用顺序散乱。
- 相同业务流程在 Runner、HMI、API 中重复实现。
- 设备切换、任务启动、runtime 启动逻辑到处散落。
- 跨模块边界不清晰，后续难以维护。

`SystemService` 的价值就在于：

```text
把系统内部能力收敛成统一对外业务接口
```

## 当前阶段建议

当前阶段推荐先做一个最小 `SystemService`，只承接最核心的四类流程：

- 模板加载与查询
- 设备注册与 active 选择
- 任务创建与读取
- runtime 启动与任务开始

不建议第一版就同时做：

- EventBus 协调
- SafetyManager 协调
- AlarmManager 协调
- 多 runtime 实例
- 复杂权限和授权

## 第一版最小接口建议

```cpp
class SystemService
{
public:
    core::Status Initialize(bool auto_connect_default_robot = false);
    core::Status Initialize(const std::string& config_file_path,
                            bool auto_connect_default_robot = false);
    void Shutdown();

    core::Status LoadTemplateLibrary(const std::string& shared_library_path);
    std::vector<platform::TemplateManager::TemplateInfo> GetLoadedTemplates() const;

    core::Status RegisterRobot(const std::string& robot_name,
                               std::unique_ptr<device::IRobot> robot);
    core::Status SetActiveRobot(const std::string& robot_name);
    core::Result<device::IRobot*> GetActiveRobot() const;
    core::Status ConnectActiveRobot();
    core::Status DisconnectActiveRobot();

    core::Result<core::Task> CreateTask(const std::string& template_name,
                                        const std::string& task_context_json);
    core::Status StartTask(const std::string& task_id,
                           const std::string& local_directory_path,
                           int start_block_index = 0,
                           int start_action_index = 0);
    core::Status PauseTask();
    core::Status ResumeTask();
    core::Status StopTask();

    runtime::ExecutionContext GetRuntimeSnapshot() const;
};
```

## 一句话总结

`SystemService` 的本质是：

```text
统一对外暴露的业务层接口，
负责把 TemplateManager、TaskManager、DeviceManager、RuntimeService
组织成稳定、清晰、可控的系统级工作流。
```
